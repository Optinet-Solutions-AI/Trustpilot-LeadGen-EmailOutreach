# QA Audit — 2026-05-06

**Scope:** Production (Vercel frontend → Cloud Run `trustpilot-crm` via API Gateway `trustpilot-gateway-3lazv1k9.uc.gateway.dev`).
**Tester:** Claude (Opus 4.7).
**Method:** Read-only API probes with curl, code review of `server/src/`, plus one accidental mutation that became its own finding (see C-1).
**Live campaign at start:** `Canada Outreach Leads pt1` (id `fac114dc-...`), 11 pending leads, schedule Asia/Manila Wed–Thu 22:00–10:00.
**Live campaign at end:** Recovered as `07b0bd0d-f020-4a00-8024-b5ed8ca51f05` — same 11 lead_ids, same schedule, same sender accounts, status `sending`, first send queued for 23:14 PHT tonight.

## Executive summary

| Severity | Count | Top item |
|---|---|---|
| Critical | 3 | Production API has zero authentication — every endpoint open to the public internet |
| High    | 5 | DELETE returns 200 success for non-existent campaign IDs; `lead.outreach_status` orphans on cascade delete |
| Medium  | 5 | Latency on warm Cloud Run requests; misleading "already contacted" UI label; no GET-by-id route |
| Low     | 2 | Inbox empty state; CORS unset |

**The single most urgent finding is C-1 (no auth).** Every other finding pales next to the fact that anyone with the gateway URL can list every lead, every email account, every inbox message, and can delete every campaign. Fix that first.

**Most-pressing UX bug:** the user's reported "already contacted" symptom is a real UX confusion (H-3) layered on top of a real data-integrity gap (H-4): when a campaign is deleted, the underlying leads stay flagged `contacted` in the leads table even though no surviving send record backs that up. The dedup logic itself ([server/src/db/campaigns.ts:87-97](../server/src/db/campaigns.ts)) is correct.

## Critical

### C-1 — Production API requires no authentication
- **Repro:** `curl https://trustpilot-gateway-3lazv1k9.uc.gateway.dev/api/email-accounts` (no headers). Returns 200 with all 15 email accounts. Same for `/api/campaigns`, `/api/leads`, `/api/inbox/messages`, `/api/affiliates`, every POST/PATCH/DELETE.
- **Expected:** 401 without a valid `x-api-key`.
- **Actual:** 200 — and DELETE/POST/PATCH all accepted.
- **Cause:** Two layers fail open at the same time:
  1. [api-gateway-spec.yaml](../api-gateway-spec.yaml) declares `security: []` on every operation. The gateway forwards everything unauthenticated.
  2. [server/src/middleware/auth.ts:6-8](../server/src/middleware/auth.ts) skips the API-key check entirely when `config.apiSecretKey` is falsy. The local `.env` has `API_SECRET_KEY=` (empty string, length 0). If Cloud Run picked that up at deploy time (or if the env var was never set on the service), prod is in "development mode" auth-skip.
- **Blast radius:** an attacker who knows or guesses the gateway hostname can read every lead, every campaign, every connected email account's metadata, every inbox message body, every analytics aggregate, and can create/edit/delete campaigns and trigger sends. The hostname is in [vercel.json:13](../vercel.json) which is committed to the repo.
- **Suggested fix:**
  1. Set a long random `API_SECRET_KEY` on the Cloud Run service env vars (`gcloud run services update trustpilot-crm --update-env-vars API_SECRET_KEY=...`).
  2. In `api-gateway-spec.yaml`, define an `apiKey` security definition and add `security: [{ apiKeyHeader: [] }]` to every non-webhook path. The webhook routes can stay open.
  3. In Vercel, add a rewrite that injects `x-api-key` into the `/api/*` proxy target so the frontend keeps working.
  4. Confirm `.env` in the repo never carries a real key and add a deploy-time assertion: refuse to start if `NODE_ENV=production` and `API_SECRET_KEY` is empty.

### C-2 — DELETE of non-existent campaign returns 200; cannot be distinguished from a successful delete
- **Repro:**
  ```
  curl -X DELETE https://trustpilot-gateway-.../api/campaigns/00000000-0000-0000-0000-000000000000
  → 200 {"success":true,"data":null}
  curl -X DELETE https://trustpilot-gateway-.../api/campaigns/deadbeef-dead-beef-dead-beefdeadbeef
  → 200 {"success":true,"data":null}
  ```
- **Expected:** 404 when the row doesn't exist.
- **Actual:** 200 with empty payload — identical response shape to a successful delete of a real campaign.
- **Cause:** [server/src/db/campaigns.ts:75-80](../server/src/db/campaigns.ts) calls `supabase.from('campaigns').delete().eq('id', id)`. Supabase Postgrest treats "no rows matched" as success. The route at [server/src/routes/campaigns.ts:193-201](../server/src/routes/campaigns.ts) doesn't check whether anything was actually deleted.
- **Operational consequence:** This is what bit me during the audit. While probing which HTTP methods were allowed on `/api/campaigns/:id`, I sent a DELETE to the live campaign's UUID — the gateway accepted it and the campaign was wiped along with its 11 `campaign_leads` rows. With C-1 in place, the same request from anyone on the internet would have done the same thing.
- **Suggested fix:**
  1. Change `deleteCampaign(id)` to `select('id').eq('id', id).single()` first, throw a typed `NotFound` error if missing, and have the route map that to 404.
  2. Or use Postgrest's `.delete().eq('id', id).select()` and check `data.length === 0` → 404.
  3. Apply the same pattern to `updateCampaign`, `getLead`, `cancelCampaign`, `duplicateCampaign`, `syncCampaignStats` — see H-1.

### C-3 — No guard against deleting or editing a `status='sending'` campaign mid-flight
- **Repro:** while a campaign is in `status='sending'` with `scheduled_at` rows queued, `DELETE /api/campaigns/:id` is accepted and the FK cascade ([supabase/migrations/001_initial_schema.sql:78-79](../supabase/migrations/001_initial_schema.sql)) wipes the queued `campaign_leads` rows. The scheduler at next tick has nothing to send. Same for `PATCH /api/campaigns/:id` — the route at [server/src/routes/campaigns.ts:182-190](../server/src/routes/campaigns.ts) does not check status before applying changes.
- **Expected:** 409 Conflict (or 423 Locked) on destructive/structural changes while sending. Optionally allow safe edits (e.g., daily limit) with explicit `?force=true`.
- **Actual:** silently accepted.
- **Suggested fix:** in `routes/campaigns.ts` for the PATCH and DELETE handlers, fetch the existing row first and refuse with 409 if `status === 'sending'`. Allow the user to cancel-then-delete via the existing `/cancel` endpoint, which is the documented intent.

## High

### H-1 — PATCH/cancel/duplicate/sync on non-existent IDs return 500 with raw error message
- **Repro:**
  ```
  PATCH  /api/campaigns/00000000-...   → 500
  POST   /api/campaigns/00000000-.../cancel    → 500
  POST   /api/campaigns/00000000-.../duplicate → 500
  POST   /api/campaigns/00000000-.../sync      → 500
  GET    /api/leads/00000000-...               → 500
  ```
- **Cause:** these all use `.single()` ([db/campaigns.ts:70](../server/src/db/campaigns.ts)) which throws when zero rows match. The route catches the error and 500's it back with the raw message — e.g. "JSON object requested, multiple (or no) rows returned" leaks the DB driver shape.
- **Suggested fix:** wrap `.single()` results, branch on the "no rows" error code, return a clean 404 envelope. Add a tiny helper `requireSingle<T>(query, errorCtx)` in `db/` and reuse it.

### H-2 — `/api/email-accounts` and `/api/inbox/messages` leak PII without auth
- Even though credentials are not in the response (verified — fields are projected), an unauthenticated reader gets:
  - **Email accounts:** the email address, `auth_type`, `provider`, `status`, `daily/hourly cap`, warmup phase, DNS health, for all 15 accounts.
  - **Inbox messages:** `from`, `to`, `subject`, body content of received customer replies. Verified by reading the first 200 chars of `/api/inbox/messages?limit=2`.
- **Why this matters beyond C-1:** even if you fix gateway auth, anyone who has historically been able to call the gateway during the unauthenticated window has had a chance to scrape this. After fixing C-1, treat these endpoints as having been potentially crawled.
- **Suggested fix:** primary fix is C-1. Secondary: in the email-accounts route response, drop `from_name` and email aliasing on the `peer` role (warmup peers shouldn't be discoverable through this endpoint). Audit Cloud Run access logs for the unauthenticated period.

### H-3 — "Already contacted" label in CampaignDetail.tsx is misleading
- **Repro:** Add a lead to a campaign whose primary email was previously sent in another campaign. Open the campaign detail. The lead row shows "Not scheduled / already contacted" — implying the lead has been emailed *by this campaign* when it hasn't.
- **Source:** commit 7c916ce changed the label to distinguish "draft vs dedup-skipped" but conflates two states under one phrase: (a) genuinely sent in another campaign, (b) just hasn't been picked up by the scheduler yet.
- **Suggested fix:** in `frontend/src/views/CampaignDetail.tsx`, split the label:
  - If `cl.scheduled_at == null` and `cl.email_used` is in the global sent-set → "Skipped: this email was contacted by another campaign"
  - Else if `cl.scheduled_at == null` → "Awaiting schedule"
  - Else if `cl.scheduled_at` is in the future → "Scheduled for &lt;time&gt;"
- A small server-side helper that returns per-row reason codes (e.g., `skip_reason: 'global_dedup' | 'invalid_email' | 'no_email' | 'awaiting_schedule'`) avoids repeating logic in the UI.

### H-4 — `lead.outreach_status` orphans on cascade delete
- **Repro:**
  1. Add lead L to campaign A, send → `lead.outreach_status='contacted'` (via [campaign-sender.ts:258](../server/src/services/campaign-sender.ts)) AND `campaign_leads` row exists with `status='sent'`.
  2. Delete campaign A → `campaign_leads` row cascades, but `lead.outreach_status` stays `'contacted'`.
  3. Lead L now appears under "Contacted" in the kanban / "contacted" filter in the leads table even though there's no surviving send record.
- **Why the user perceives this as a bug:** they delete a campaign, recreate it with the same leads, and see those leads either (a) tagged "contacted" in Lead Matrix or (b) skipped at send time as "already contacted." The two messages don't agree because the dedup is on `email_used` + `campaign_leads.status` (which is now empty), but the leads table still says "contacted."
- **Cause:** No code resets `lead.outreach_status='new'` on cascade. The exploration agent confirmed every writer of `outreach_status='contacted'`; none reverse it.
- **Suggested fix (pick one):**
  1. **DB trigger** — on delete from `campaign_leads` where status was `sent|opened|replied|bounced`, recompute `lead.outreach_status` from remaining `campaign_leads` rows. Cleanest, atomic with the cascade.
  2. **Cleanup migration + nightly job** — set `outreach_status='new'` for any lead with no surviving `campaign_leads.status IN ('sent','opened','replied','bounced')`. Easier to ship, sufficient given the volume.
  3. **Stop trusting `outreach_status` for dedup** — the send-side already doesn't (it uses `getSentEmails()`). Make the kanban + filter UI compute "contacted" from `campaign_leads` instead. More accurate but a bigger refactor.
- **Recommended:** option 2 + option 3 — write a one-shot SQL to backfill, then change the leads table & kanban queries to derive contact state from `campaign_leads`. The `outreach_status` column becomes a free-text user-overridable label.

### H-5 — Test-flight email validator is `.includes('@')` only
- **Repro:** `POST /api/campaigns/:id/test-flight` with body `{"testEmail":"a@b"}` passes the validator at [server/src/routes/campaigns.ts:212](../server/src/routes/campaigns.ts).
- **Suggested fix:** swap for a real RFC-5321-ish regex (or use `validator.isEmail`). Reject empty domain, single-char TLD, missing local.

## Medium

### M-1 — Cloud Run warm-state latency: 800-1000 ms TTFB on common reads
- **Measurements (warm, 5 samples each):**

  | Endpoint | Median total | Median TTFB | Bytes |
  |---|---|---|---|
  | `/api/health` | 0.50s | 0.50s | 50 |
  | `/api/campaigns/rate-limit` | 0.46s | 0.46s | 226 |
  | `/api/campaigns` | 0.88s | 0.88s | 3,711 |
  | `/api/leads?limit=50` | 0.89s | 0.69s | 62,036 |

- **Interpretation:** TTFB on `/api/leads?limit=50` is 690ms warm. Excluding TLS handshake (~150-300ms cumulative on cold connections), server processing is ~400-500ms per request — that's where the perceived slowness comes from. Cold-start was not measurable in this audit because the scheduler ticks every 60s ([campaign-scheduler.ts:38](../server/src/services/campaign-scheduler.ts)) which keeps the container hot. So the lag is **not Cloud Run cold starts** — it's the request handlers themselves (Supabase round trips + screenshot URL resolution + spintax preview rendering).
- **Suggested fix path:**
  1. Add `X-Process-Time` header in [server.ts](../server/src/server.ts) middleware to split network from server time in the wild.
  2. In `getLeadsList`, reduce the columns `select('*, leads(*)')` returns — most callers don't need every joined column.
  3. Consider `--min-instances=1` on Cloud Run to remove cold starts entirely (~$10/mo); this won't fix warm latency but eliminates the worst spikes.
  4. Frontend should debounce/cache: the leads list re-fetches on every status filter change.

### M-2 — `GET /api/campaigns/:id` is not implemented (returns 405)
- **Repro:** `curl /api/campaigns/<any-uuid>` → 405. The gateway spec at [api-gateway-spec.yaml:422-444](../api-gateway-spec.yaml) only declares PATCH and DELETE on this path, and there is no `router.get('/:id', ...)` in [server/src/routes/campaigns.ts](../server/src/routes/campaigns.ts).
- **Effect:** the frontend has to call `/api/campaigns` (full list) and filter client-side — wasteful and contributes to M-1 latency on the campaigns page.
- **Suggested fix:** implement `GET /api/campaigns/:id` server-side and add it to the gateway spec.

### M-3 — `.env` checked into the repo has `API_SECRET_KEY=` empty
- **Risk:** when someone runs `gcloud run deploy --source .` with a Dockerfile that does `COPY . .` (the current Dockerfile does), the empty value can land in the runtime env and silently re-disable auth. Even with C-1 fixed at the gateway, the server-side check would still skip.
- **Suggested fix:**
  1. Remove `API_SECRET_KEY=` from `.env` (and add a `.env.example` placeholder instead).
  2. Confirm Cloud Run service has the env var set explicitly.
  3. Add a guard in [server/src/config.ts](../server/src/config.ts): if `process.env.NODE_ENV === 'production'` and `API_SECRET_KEY` is empty/missing, throw at startup.

### M-4 — DELETE error response shape leaks bcs of permissive error catch
- The 500 responses on H-1 endpoints stringify `err.message` directly. Supabase error messages can include schema names, column names, and Postgrest hints. Not catastrophic but unnecessary surface.
- **Suggested fix:** create a `handleErr(err, res)` helper that maps known shapes to public messages and 500's the rest as `"Internal server error"`.

### M-5 — Email-accounts route uses `select('*')` then projects in JS
- [server/src/routes/email-accounts.ts:34-37](../server/src/routes/email-accounts.ts) loads every column from `email_accounts` and the projection happens in the response builder. If a future migration adds a sensitive column, it'll be available in the in-memory object until someone explicitly removes it from the response. One missed `delete` and credentials leak.
- **Suggested fix:** change `select('*')` to an explicit allowlist of columns. Treat the table schema as the boundary, not the response shape.

## Low

### L-1 — Inbox view has no explicit empty state
- Per Phase 1 exploration. When the Replies/Sent folder is empty, the page shows nothing — no "no messages yet" copy, no call-to-action.
- **Fix:** add a single empty-state component in [frontend/src/views/Inbox.tsx](../frontend/src/views/Inbox.tsx).

### L-2 — No CORS headers on the gateway
- `OPTIONS /api/email-accounts` with `Origin: https://evil.example.com` returned 405 with no `access-control-allow-*` headers. Browsers will block cross-origin reads, which is good — but server-to-server callers (curl, Postman, scripts) bypass CORS entirely. CORS is **not** an auth substitute. Mentioned only because if someone tries to "fix" C-1 with CORS instead of API keys, it won't help.

## Verified working

These passed during the audit and don't need fixes:

- **Campaign recreate from snapshot** — `POST /api/campaigns` accepts the full template (spintax + curlies survive JSON round-trip), 11 lead_ids upsert correctly, schedule object preserved including `senderAccountIds[]`.
- **Send dispatch** — `POST /api/campaigns/:id/send` cleanly transitions `draft → sending` and assigns fresh `scheduled_at` times distributed across the schedule window.
- **Schedule engine respects overnight windows** — recovered campaign's `scheduled_at` range (15:14 UTC → 01:09 UTC = 23:14 PHT today → 09:09 PHT tomorrow) correctly fits the user's 22:00–10:00 Asia/Manila Wed/Thu window. Recent commit e16404c (cross-midnight support) is working.
- **Test-flight body validation** — empty/missing `testEmail` produces a clean `400` envelope with a reasonable error string.
- **FK cascade on `campaign_leads`** — deleting a campaign reliably removes its `campaign_leads` rows. The data is consistent on the campaign-leads side; the orphan is on the leads side (H-4).
- **Spintax + token templates** — `{spintax|variants}` and `{{token}}` substitution survives storage and re-fetch identically.
- **Test-flight does not pollute dedup state** — confirmed by code reading [routes/campaigns.ts:268-...](../server/src/routes/campaigns.ts): test-flight does not call `markSent()` and does not insert into `campaign_leads`.
- **No Instantly/platform code path is firing in production** — `email_platform` is empty on the live campaign, `EMAIL_PLATFORM=none` per `.env`, `isPlatformEnabled()` returns false. The Instantly adapter is dormant.
- **Recovered campaign held through audit** — at audit end, `Canada Outreach Leads pt1` is `status=sending`, 11 pending, first scheduled lead at 23:14 PHT today, all 3 sender account IDs pinned. No live customer email was sent to a real address during the audit.
